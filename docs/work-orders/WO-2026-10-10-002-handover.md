# Handover: serial flood guard for `local-serial-log-forwarder`

From: architect (Claude, app). To: the forwarder repo's agent. Date: 2026-10-10.
Owner and approver: Chip. Chip merges, deploys to the Pi and does all device operations.
This is a handover, not a work order. Your repo's own workflow doc and rules govern how the work is run (Step 0 before any code, review rounds, closing record). Where this note and your repo's rules disagree, your repo wins; tell Chip.

## 1. Goal (plain language)

When the firmware floods the serial port with the same message thousands of times, the forwarder should send AWS only three things for that run: the first line, one summary ("repeated N times"), and the last line before normal output resumes. Everything else stays as it is.

**AWS only.** The Pi's own log file (`/var/log/serial-forwarder/<name>.log`) and stdout keep every line, unchanged. Reason: AWS is a diagnostic copy and the problem there is cost and noise. The raw local log is the only place the full flood stays visible for firmware debugging.

Chip's constraint: this is an edge case. Keep it simple and cheap. If it starts growing gates, flags or config, stop and ask him to pare it back.

## 2. What happened (evidence, not opinion)

Source: fleet-ops evidence record `WO-2026-10-10-001-evidence.md` (branch `wo/2026-10-10-001-serial-flood-evidence`, commit b027f8a). Ask Chip for it if you cannot reach that repo.

- Boron-Dev-09, 2026-10-09 06:26:29 to 06:36:29 UTC, about 10 minutes. 653 serial events reached AWS (650 log lines, 3 lifecycle events).
- 612 of the 650 lines (94%) were one message, TimeDiag. Not byte-identical: the uptime prefix, epoch and time digits change from line to line, and the device truncates the line at 182 characters with `~`, with three different tails.
- The forwarder's own throughput set the rate, about 65 lines a minute at roughly 0.86 s per line, because it makes one blocking POST per line. The device emitted far faster in bursts. Lines were lost before the forwarder (merged lines and fragments appear in the capture).
- Impact was small: no errors, no throttles, no health escalation, under 2 cents. The point is cost and noise growth, not an outage.

## 3. Facts about your code (from fleet-ops' read at e27bce8, `src/serial_reader.py`, 148 lines)

Verify every one of these yourself in Step 0 before relying on it. The code running on the Pi was never verified and may differ from e27bce8.

- One daemon thread per device (`monitor_device`, :73); a device's lines are handled in order by one thread, so per-device state needs no locking.
- `readline()` (:97) returns at a newline or after the 1 s timeout (:91); empty reads loop (:98-99); decode and strip at :101; empty lines skipped (:102).
- Per line: `write_log` (:103) prints to stdout (:65), appends to the local file (:67-68), then calls `post_to_api` (:70).
- `post_to_api` does one blocking `requests.post`, 3 s timeout, no retry (:44-49); a failure is printed and the line dropped (:51-58).
- The only state kept between lines is `last_state` (:77), the lifecycle state.
- Natural seam: inside `write_log`, between the file append and `post_to_api` (:70). Skipping a POST also removes the 0.86 s per line cost, so the thread reads faster.

## 4. Decisions already made

1. AWS only (section 1).
2. A "run" is consecutive lines whose match key is equal. Suggested key: the line with all digits replaced, compared on the first 80 characters. Measured on the flood: 51 runs, 650 lines down to 77 events (88%). Exact-byte matching collapses 0% and must not be used. A looser key (module, level and first word) reaches 94% but can merge different messages, so it is not recommended; Step 0 may propose a different key with evidence, and Chip decides.
3. A run of 1 or 2 lines sends everything normally. From 3 lines up: first line sent at once; the middle lines are not posted; when the run ends, send one summary and then the last line, then the new line as normal.
4. Per-device state lives in the thread (previous key, run count, the held last line). No new files, config, flags or dependencies.
5. Lifecycle events (connected, disconnected, missing) are not collapsed and always flush a pending run first.

## 5. Constraints the AWS side imposes (checked in fleet-ops at 685bd0d)

- Severity is parsed from the posted text by the ingestion Lambda: `lambda/src/utils/parse.ts:184-188`, the first whole word matching TRACE, INFO, WARN or ERROR, case-insensitive, anywhere in the line. The serial branch then sets device health from it ([current-state.ts:328-332](lambda/src/storage/current-state.ts)). Therefore the summary line must contain the word INFO before any other severity word and must not quote the collapsed text. Suggested form: `[forwarder] INFO: previous line repeated N times`.
- The held last line must be sent as received, so the severity and `lastSerialLogLine` of the final posted line stay true.
- Do not change the Lambda or the posted payload shape. If you believe that is needed, stop and tell Chip.

## 6. Open design points for Step 0 (keep each to one line of answer)

- How a pending last line is flushed when the device goes silent (the 1 s read timeout at :98-99 is the natural trigger) and on disconnect (:105-108). It must never be held indefinitely or lost.
- Whether the key should ignore the truncated tail (the three `~` variants).
- Confirm the summary is posted in order, between the run's first line and the last line, from the AWS side's point of view.
